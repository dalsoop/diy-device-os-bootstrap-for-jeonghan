# Contracts

## Common conventions

The repository exposes command-line, JSON, filesystem, and MCP interfaces. Usage errors, invalid input, rejected safety checks, failed downloads, and incomplete operations exit nonzero or return a tool error. Human prose is informational; automation consumes versioned JSON or documented files.

Stable IDs use lowercase ASCII letters, digits, and hyphens. Configured repository paths are relative, normalized, non-empty, contain no empty, `.` or `..` segment, and remain inside their declared root. Unknown enum values, duplicate identities, duplicate destinations, and ambiguous target state are errors rather than fallback cases.

## World Playbook

`burn-history/.paths.yaml` uses API version `device-os.bootstrap/v1alpha1` and kind `WorldPlaybook`. It lives in the user folder, and every path it registers is relative to that folder and must stay inside it. It declares `Asia/Seoul`, the draft `jeonghan-home` at `home.yaml`, the completed-generation root `logs/usb`, and generation format `{YYYYMMDDHHmmss}-{world-slug}`.

A draft World contains unique assets, networks, nodes, services, media definitions, one valid `defaultMedia`, the overlay selection, and fail-closed policies. References resolve exactly once; static addresses are unique and belong to the referenced network; the gateway is directly reachable or has an explicit route. Supported presentation languages are `ko-KR` and `en-US`.

`spec.overlays` is required in every World: a non-empty list of unique values from the closed set `tailscale`, `netbird`. A missing field, an empty list, a duplicate, an unknown value, a non-string value, or a non-list fails validation; there is no default.

The resolver emits versioned JSON (`schema_version` 1) containing source paths, World identity, selected media ID, ordered entry IDs, language, the top-level `overlays` array in the order written in the World, and policy. When the Installer resolves media, the World order must exactly match the final entry order. A caller may choose another declared media ID but may not invent one. A resolved media plan embeds this World plan, so its digest also binds the overlay selection.

The current `jeonghan-home` contract declares `inventory-capture=[debian-live]`, default `dns-install=[dns-appliance]`, and `overlays: [tailscale, netbird]`. A DNS media definition requires guarded unattended policy; every World requires exact hardware matching, one internal target disk, target-specific erase confirmation, and no automatic boot timeout.

## Catalog interfaces

`engine/catalog/data/index.json` uses `schema_version: 1` and is the closed-world registry. Every referenced JSON file exists, every controlled JSON file is registered, and IDs and paths are unique. `engine/catalog/bin/verify-catalog` exits zero only when the complete registry and semantic contract pass; it emits no media and changes no repository state.

A public media entry uses schema version 2 and provides stable ID, group, release version, optional architecture, safe `images/*.iso` destination, menu alias, non-empty Korean and English descriptions, interactive/live boot behavior, `profile_adapter: none`, a `locked-download` source, and mandatory redistribution metadata. The source contains a basename-only filename, HTTPS URL, and lowercase 64-character SHA-256. A bootloader also uses schema version 2 and provides stable identity, implementation, version, safe archive root, locked source, and redistribution metadata.

`personal-use-only` contains only its status. `redistribution-reviewed` binds the review to the record's exact version, source URL, and source SHA-256 and requires a reviewer, review date, all four evidence kinds, and exactly one disposition for each license-text, notices, corresponding-source, and trademark obligation. Changing the version, URL, or digest invalidates the review. Current records are personal-use-only.

Published schemas reject extra properties. CI validates every tracked Catalog record and explicit valid and invalid fixtures against the schemas. The executable jq validator and Installer consumer remain independent implementations, so schema coverage does not prove complete semantic parity for documents outside the tracked and simulated cases.

## Installer composition and resolved media plan

`engine/installer/usb-media/composition.json` uses `schema_version: 1` and names product/repository identity, Catalog path and index, bootloader ID, reference collection, local-entry registry, USB labels and reserves, and safe repository bundles.

The resolved media plan records the repository commit, Catalog tree, product, USB properties, one bootloader, groups, ordered public/local entries, and bundles. A World-driven plan embeds the validated World plan. Public and local registries may not expose the same ID; entry IDs, source filenames, and destinations are unique.

Supported entry behaviors are `interactive-installer`, `live-environment`, and local `guarded-unattended`. Supported source kinds are `locked-download` and caller-supplied `runtime-artifact`; supported adapters are `none` and `dns-appliance`. A runtime artifact uses an absolute caller path and matching manifest whose digest names that exact artifact. Unknown kinds or adapters fail.

Repository bundles use `repository-file` or `repository-tree` with contained source and destination paths. Because current staging can follow symlinks without resolved-target containment, a tracked bundle containing any symlink is outside the accepted contract.

## Capacity JSON

Schema version 1 reports each selected entry's size and source, verified total, estimated total, fixed reserve, layout overhead, unknown IDs, unverified IDs, target capacity, `required_bytes`, and `fits`. Decimal units such as `16GB` and binary units such as `16GiB` are accepted. Remote header or one-byte probes are estimates. Exact final fit exists only when every selected artifact is locally verified.

## USB filesystem result

The data partition label is `DEVICE-OS`. It contains staged images, bundles, Ventoy configuration, resolved media metadata and digest, image checksums, guides, tools, project license, license history, third-party notices, the license text of each overlay client the DNS image selects (`Tailscale-BSD-3-Clause.txt`, `NetBird-BSD-3-Clause.txt`), source revision/archive information, and `manifests/LICENSES.SHA256`.

When the DNS adapter is selected, a separate FAT32 `DNS-ENROLL` partition stores `installer.json`, public enrollment evidence, encrypted recovery generations, active pointers, and reinstall authorizations. `installer.json` is schema version 1 with `build_id`, `image_sha256`, `debian_point_release`, `technitium_version`, `technitium_image_digest`, `overlays`, and only the selected overlays' `<overlay>_version` and `<overlay>_archive_sha256` fields; first boot reads only `build_id` and `image_sha256`. FAT32 is readable by the signed Debian Installer kernel's FAT modules; exFAT is unsupported at this stage. Files must remain below FAT32's 4 GiB per-file limit. It is transport, not the long-lived secret store. The Ventoy `DEVICE-OS` data partition remains exFAT.

A completed personal World generation contains immutable `world.yaml`, `world.lock.json`, `media-manifest.json`, `verification.json`, and `event.json`. The event recorder seals `{YYYYMMDDHHmmss}-{world-slug}` before invoking the target-specific writer, requires the writer's schema-version-1 redacted write evidence with passed readback and a device that equals the requested target, publishes `event.json` and `verification.json` at schema version 2 without the device path, then atomically renames the staged directory into `burn-history/logs/usb/`. It excludes images, caches, credentials, private keys, raw serials, MAC addresses, UUIDs, and recovery material.

The recorder holds one checkout-local lock across each physical write. Failed, cancelled, and recovered interrupted attempts never create a generation; they publish schema-version-2 records without the device path under `burn-history/logs/usb/failed/YYYY/{event-id}.json`. The required check validates every published record against `engine/world/schemas/usb-event.schema.json` and `usb-verification.schema.json`. A successful event lives inside its generation. Simulations, plans, builds, and capacity checks create no event. Git commits and pushes remain an explicit pull-request workflow rather than a side effect of the root writer.

## DNS enrollment record

Appliance SSH and Cockpit use the `dns-operator` account. The encrypted
`secrets/operator-password` filename remains the recovery credential key.

`public.json` uses schema version 1 and records generation UUID, hostname, role, fixed address, hardware identity, installer build and image digest, public SSH and certificate fingerprints, service health, and completion time. It never contains a password, token, or private key.

A generation is complete only when `public.json`, `recovery.tar.age`, the sanitized install log, and `COMPLETE` exist and the role's `ACTIVE` pointer names that generation. Reinstall authorization names the same active generation and matching system UUID hash; an authorization for an older generation is invalid.

## DNS management commands

`engine/installer/management/network-preflight --json <router-cidr>` returns schema-version-1 topology, LAN reachability, optional outbound IP/DNS/HTTPS probes, phase gates, and blockers. The gates `network_gates.post_install_tailscale` and `network_gates.post_install_netbird` each carry `internet_required: true` and the same `ready` value: Internet ready and every node reachable, or `null` when the Internet is not checked. `--offline` reports Internet readiness as unknown. It does not establish DNS health or installation evidence.

`dnsctl health` reads a fixed node. `dnsctl plan <zone-file> [--out <plan-file>]` prints a plan and a human diff. The zone name comes from the SOA owner, or from `$ORIGIN` when the owner is `@`; the forward zone `burn-history/dns-records.zone` (`home.arpa`) and the reverse zone `burn-history/dns-reverse-records.zone` (`77.10.in-addr.arpa`) both qualify. The plan is a JSON object with `schema_version` 2, `created_at`, `zone`, `target_url`, `source_commit`, `zone_path` (relative to the Git work tree), `current_sha256`, `desired_sha256`, and `changed`; `source_commit` and `zone_path` are null when the zone file is untracked or modified. `current_sha256` is the SHA-256 of the exact live export and `desired_sha256` of the exact zone file. `changed` is false only when both have the same record set without the SOA and apex NS records, which the cluster manages: each record is compared as `<owner> <ttl> IN <TYPE> <data>` with absolute lowercase names (owners and the name fields of NS, CNAME, PTR, DNAME, MX, SRV, and SOA data), the TTL in seconds (explicit, else `$TTL`, else the previous record's), and single spaces outside quoted text, ignoring order, duplicates, comments, and parentheses. The human diff on stderr is a unified diff of those two record sets. Plan fails without printing a plan when the export is a Technitium JSON error instead of zone text, when either side uses a directive other than `$ORIGIN` and `$TTL`, a class other than `IN`, unbalanced parentheses, or a record without type, TTL, or the data-field count its type needs, and when the import payload (below) of the zone file would not carry exactly its record set without the SOA and apex NS. `--out` requires a committed, unmodified zone, saves the object once with mode 0444 through a hard link that never replaces an existing name, and prints `dnsctl: plan_sha256=<sha256>` on stderr.

`dnsctl apply --plan <plan-file> --plan-sha256 <sha256> --confirm APPLY` hashes one private copy of the plan and writes only when all of these hold: the hash matches; the plan is a saved schema-version-2 plan; `TECHNITIUM_URL` equals `target_url`; `HEAD` equals `source_commit`; the zone file is tracked, unmodified, and hashes to `desired_sha256`; its import payload carries exactly its record set without the SOA and apex NS; the live zone still hashes to `current_sha256`, so any change of the exact export since the plan, an SOA serial included, is drift; and the audit log has no successful apply of the same `plan_sha256`. The import payload is the zone file without its SOA record and without lines whose owner is `@` and whose type is NS, the rule `cluster-bootstrap` uses; apply posts it to `/api/zones/import` with `overwrite=true&overwriteZone=true`, so the cluster keeps its own SOA and apex NS. A plan with `changed` false returns `{"status":"unchanged"}` without writing. Success prints `{status, plan_sha256, response}`. The command returns nonzero for authentication, TLS, state, drift, replay, or API failure and appends redacted audit JSONL, carrying `plan_sha256` for saved plans, for completed plan/apply outcomes and live-zone drift. It does not prove pull-request approval or require unrelated checkout files to be clean.

Restore requires an explicit target URL and `RESTORE <exact-url>`, decrypts and validates the archive locally, then currently sends the token and backup with TLS certificate verification disabled. That interface is limited to isolated recovery drills and is not a production-qualified restore path. Backup collection accepts only encrypted outputs. Tailscale enrollment accepts protected OAuth credential-file paths, not credential values, and creates one short-lived node key at a time. NetBird enrollment accepts a protected token-file path, not the token, and creates one one-off setup key at a time.

`DNS_APPLIANCE_INSTALL_MODE=reviewed` is the default and requires exactly one enabled embedded inventory, read from `burn-history/os-installs/<role>/hardware.conf`. `guided` uses the disabled network profiles `burn-history/os-installs/<role>/os.conf`. `DNS_APPLIANCE_INVENTORY_DIR` replaces `burn-history/os-installs` as the directory that holds the per-role folders in both modes. Both modes install Debian OS and the offline DNS payload together. The embedded `install-mode` and manifest `install_mode` name the selected mode; a missing mode means `reviewed`, and unknown modes fail.

In guided mode, Debian Installer's debconf frontend asks for role and wired physical NIC, captures local DMI/NIC/disk hashes into `/run/dns-appliance/inventory`, and displays the address, gateway, disk model, serial and exact byte count. It requires `ERASE <role> /dev/<disk> <serial> <bytes>`. Capture never writes the internal disk. The `select-disk` phase rechecks the captured hardware, disk path and exact size, single eligible internal disk, installer ancestry, mounted state, confirmation and active-generation reinstall authorization before signature clearing. An additional internal disk blocks guided installation even when its identity differs. Runtime inventory and confirmation are volatile and are never embedded or committed.

A build does not authorize media or internal-disk writing. Its manifest is paired with the DNS runtime artifact during capacity and burn. `check-readiness` uses the same mode environment, requires the cached inputs of the World's selected overlays only, and rejects a mismatched ISO manifest or a manifest whose `overlays` differ from the World's.

The installer step `dns-finish-install` reads the embedded `overlays` file and stops the installation when it is missing, empty, or not a canonical selection. It copies the selection to `/etc/dns-appliance/overlays` in the same format, installs `tailscale`, `tailscaled`, and the upstream Tailscale unit only with Tailscale, and installs `/usr/bin/netbird` plus the repository's `netbird.service` (daemon socket `unix:///var/run/netbird.sock`, profile `/var/lib/netbird/default.json`, logs under `/var/log/netbird/`) only with NetBird. First boot enables exactly the selected daemons and fails on an invalid selection file. No overlay client is enrolled during installation. Guided mode removes the separate capture/rebuild round trip; it does not establish VM or physical installation proof.

Capture, the inventory wizard and the install gate use the same read-only `disk-identity` adapter, bundled beside the capture tools and the ISO gate. Kernel model/serial attributes are preferred; SATA serials may come from `ata_id --export` on the exact candidate block device. Failed, empty or ambiguous identity evidence is rejected, and the serial is re-read before disk preparation.

## DNS redistribution records

The distribution policy lists the full known component-ID set in canonical order: `debian-package-closure`, `technitium-oci`, `tailscale-archive`, `tailscale-dependency-report`, `netbird-archive`, `repository-source-snapshot`. The DNS component registry is schema version 1 and contains exactly the canonical-order subset implied by the image's overlay selection: the Debian package closure and Technitium OCI archive, then the Tailscale archive and Tailscale dependency report only with Tailscale, then the NetBird archive only with NetBird, then the repository source snapshot. The registry carries no `overlays` field; `verify-distribution-contracts` derives the selection from its overlay components and rejects a missing, extra, or reordered component. Each component binds a stable ID and immutable version to the SHA-256 of the exact bytes or closure manifest used by the build. Technitium additionally binds its OCI manifest digest. Current component redistribution states are personal-use-only. The component-review record's ID enum includes `netbird-archive`.

A reviewed component record binds reviewer evidence and obligation dispositions to the exact component ID, version, digest, and, for Technitium, OCI source identity. The build manifest (schema version 1) preserves the final ISO digest, component registry digest, policy digest, the required `overlays` (one of `[tailscale]`, `[netbird]`, `[tailscale, netbird]`), the component statuses in the same canonical-order subset, SBOM digest, exact source locks, and repository source identity. `tailscale_version` and `tailscale_archive_sha256` are present if and only if Tailscale is selected, and `netbird_version` and `netbird_archive_sha256` if and only if NetBird is selected. With a manifest, `verify-distribution-contracts` also binds its overlays, components, versions, and digests to the registry. The SPDX SBOM describes `SPDXRef-Tailscale` and `SPDXRef-TailscaleDependencyReport` only with Tailscale and the `netbird-linux-static` package `SPDXRef-NetBird` (license declared `BSD-3-Clause`, concluded `NOASSERTION`) only with NetBird. `check-license-policy`, both Linux writers, and the schemas apply the same conditional shape. The third-party notices and distribution status bundled into the ISO list only the selected overlays. Build tooling records evidence but cannot create reviewed status.

`license check` enumerates DNS components from a valid build manifest's `overlays`; without one, a World-driven personal-use check uses the World plan's overlays, and the World-less reference collection lists all six known components.

A DNS final review record is separate from component review. It binds the final ISO SHA-256 to the exact component registry and build manifest digests and records all four evidence and obligation classes. Prebuilt evaluation requires both fully reviewed components and this final record, verifies the bound SBOM and staged obligation files, and rejects `NOASSERTION`. Missing or mismatched evidence fails closed.

The repository-wide distribution policy enables source release and disables generated-artifact and prebuilt release. Even after a future successful CLI decision, publication must independently pass the protected GitHub Environment `prebuilt-distribution` with a human-only required reviewer. The CLI has no Environment-approval input and performs no upload.

## Read-only status monitor

`engine/installer/management/dns-appliance-status-monitor/start` accepts server arguments after requiring Python 3. `--config <json>` is required by the Python entry point; the wrapper supplies its bundled config. `--listen` defaults to `127.0.0.1`, `--port` to `8080`, and `--check-once` prints a JSON array instead of listening.

The configuration contains at least one node with exactly `name`, `host`, and `query`. `host` is a DNS name of one or more valid labels or an IPv4 address; the bundled configuration uses `dns01`, `dns02`, and `dns03`. Invalid JSON, an empty node set, a missing field, an `address` field, an invalid host, invalid DNS label, unavailable bind address, or occupied port terminates nonzero. The management host's resolver decides the network path of a name and must resolve the role names without depending on the DNS cluster (a hosts file or an overlay's own DNS).

`--check-once` prints, per node, `name`, `host`, `resolution` (`ok`, `detail`), `checks`, and `reboot` with `pending` (boolean), `skipped_consecutive` (integer), and `last_skip` (RFC 3339 UTC string). A host that does not resolve is reported as a failed `resolution` for that node, with its probes marked not probed, not as a crash. The reboot values come from one GET of `http://<host>:9100/metrics` (`dns_appliance_reboot_pending`, `dns_appliance_reboot_skipped_consecutive`, `dns_appliance_reboot_last_skip_timestamp_seconds`); each is `null` when the endpoint is unreachable or the metric is absent, and `last_skip` is also `null` when the metric is `0`. Probe failures are returned as `ok:false` status data and do not trigger mutation.

In server mode, `GET /` and `GET /index.html` return UTF-8 HTML with `Cache-Control: no-store`; every other path returns 404. Each refresh probes DNS UDP/TCP 53 and TCP reachability for Cockpit 9090, Technitium 53443, and metrics 9100, reads the reboot metrics, and highlights a node with one or more consecutive skipped reboots. There is no authentication or write endpoint, so a non-loopback `--listen` requires separately managed access control.

## Appliance update and reboot state

The installed appliance updates from `https://deb.debian.org/debian` (`trixie`, `trixie-updates`) and `https://security.debian.org/debian-security` (`trixie-security`), components `main non-free-firmware`, signed by `debian-archive-keyring`. `apt-daily-upgrade.timer` installs at dns01 02:00, dns02 02:30, dns03 03:00 and `dns-appliance-reboot.timer` fires at dns01 03:00, dns02 03:30, dns03 04:00, both `Asia/Seoul`, with no random delay and no catch-up after downtime. `/etc/dns-appliance/peers` lists the two peer roles and their addresses from the embedded role profiles.

`/run/reboot-required` is written only by the appliance's kernel hook `/etc/kernel/postinst.d/zz-dns-appliance-reboot-required`, which a kernel package's postinst runs through `run-parts` with `<kernel-version> <image-path>`. The hook atomically writes `*** System restart required ***` to `/run/reboot-required` (mode 0644) and adds `DPKG_MAINTSCRIPT_PACKAGE`, or `linux-image-<kernel-version>` when that is unset, to `/run/reboot-required.pkgs` once. It always exits zero; a marker it cannot write is reported on stderr in the APT log and does not fail the kernel installation. `/run` is a tmpfs per boot, so a marker never outlives its boot, and the installer's own kernel installation runs before the hook is installed. Only a kernel package writes the marker; an updated library reaches a running service when that service restarts or at the next reboot.

`dns-appliance-reboot window` probes each peer with a UDP DNS query (2-second timeout, retried once), adds every answering peer to `/var/lib/dns-appliance/reboot-seen-peers`, does nothing more without `/run/reboot-required`, reboots when no seen peer fails, and otherwise logs the failing peers under the journal tag `dns-appliance-reboot`, increments `reboot-skips-consecutive`, and records `reboot-last-skip` (Unix seconds). A skipped window exits zero. `dns-appliance-reboot metrics` prints the three `dns_appliance_reboot_*` gauges that the health timer writes to the node-exporter textfile `dns-appliance-reboot.prom`; unreadable state removes that file.

## Appliance firewall and health output

`dns-finish-install` renders `/etc/nftables.conf` from `engine/installer/dns-image/payload/nftables.conf` with the role profile's `lan_cidr` and `management_cidr` (each must be one IPv4 CIDR), the three addresses of the embedded role profiles, and `/etc/dns-appliance/overlays`; lines for an unselected overlay are dropped, and an invalid input or an unrendered marker stops the installation. The file defines only `table inet dns_appliance` with the chains `overlay_prerouting` (prerouting, policy accept; drops traffic for a local, broadcast, or multicast address on a selected overlay interface unless it is established or related, ICMP/ICMPv6, UDP/TCP 53, or TCP 22, 9090, 9100, 53443), `input` (policy drop), `forward` (policy drop), and `output` (policy accept). It is installed with the drop-in `/etc/systemd/system/nftables.service.d/60-dns-appliance.conf`: `ExecStop=/usr/sbin/nft destroy table inet dns_appliance` and `ExecReload=/usr/sbin/nft -f /etc/nftables.conf`, each replacing Debian's command. First boot sets Technitium's `DNS_SERVER_RECURSION_NETWORK_ACL` to `127.0.0.0/8`, the LAN, then `100.64.0.0/10` with Tailscale and `10.78.0.0/16` with NetBird.

`dns-appliance-health` writes `/var/lib/dns-appliance/health.json` with `hostname`, `address`, `dns_udp`, `dns_tcp`, `technitium`, `cockpit`, `ntp_synchronized`, `overlays`, and `checked_at`. `overlays` holds one object per selected overlay and no other: `tailscale` `{up, state, ip, hostname, tags}` from `tailscale status --json` (`up` is 1 when the state is `Running`) and `netbird` `{up, state, ip, hostname}` from `netbird status --json` (`state` is `Connected` or `Disconnected` from the management connection, `ip` without its prefix length, `hostname` the first FQDN label). A daemon that cannot be read reports `up` 0 and state `Unavailable`. The node-exporter textfile `dns-appliance.prom` carries `dns_appliance_service_up` for `dns_udp`, `dns_tcp`, `technitium`, `cockpit`, `ntp`, and `service="tailscale"` or `service="netbird"` for each selected overlay only. An invalid overlay selection file makes the health run fail. Enrollment `public.json` does not change.

## Agent Gateway

The gateway is accessed through MCP stdio locally or a management-host forced SSH command over an overlay network (Tailscale or NetBird). Every tool returns structured output or a tool error. Output is clipped at 64 KiB but is not content-redacted, so delegated commands must keep credentials out of stdout and stderr.

| Tool | Input | Output | Error and authority boundary |
| --- | --- | --- | --- |
| `repository_status` | None | Revision, branch, dirty-file list | Local read only |
| `world_validate` | Optional `dns-install` or `inventory-capture` | Delegated validation result | Rejects other media; no download/write |
| `world_plan` | Optional media | Delegated selected plan | No download/write |
| `world_simulate` | Optional media | Delegated skipped-phase simulation | No download/write |
| `world_capacity` | Capacity string, network-probe boolean, optional media | Delegated capacity JSON | Network probes default off; no write |
| `network_preflight` | Router CIDR and Internet-check boolean | Topology/reachability JSON | Fixed probes only; no repair |
| `tunnel_status` | None | `schema_version: 2` with `data.overlays.tailscale` and `data.overlays.netbird`, each `{available, management_host: {hostname} or null, dns_nodes: {<role>: {online, addresses}}}` for only `dns01`–`dns03`; Tailscale adds `backend_state`, NetBird adds `management_connected` | Reads `tailscale status --json` and `netbird status --json` from `DEVICE_OS_AGENT_TAILSCALE_COMMAND` / `DEVICE_OS_AGENT_NETBIRD_COMMAND` (absolute executable paths) or `PATH`; an overlay whose CLI is absent reports `available: false`; tool error when neither CLI exists, a present CLI fails or returns invalid output, or a set command variable is not an absolute executable path |

| `dns_apply` | Fixed role, lowercase 64-character `plan_sha256` of a plan saved by `dns_plan`, exact `APPLY home.arpa TO <role> PLAN <plan_sha256>` | Delegated apply result | Always discoverable but rejects calls unless host policy is enabled; rejects an unknown plan; requires applier token and trusted CA plus all `dnsctl` gates |

There is no gateway interface for USB burn, OS installation, restore, reinstall authorization, enrollment, router mutation, arbitrary shell, arbitrary path, arbitrary URL, or raw credential input.

`install-gate validate-profile <file> <role>` validates unique fields, required values, IPv4 ranges, prefix/netmask agreement, LAN membership, gateway reachability, management subnet containment and safe domain fields without reading hardware or writing disks. Image build, readiness and guided capture share this validator.

`fetch-debian-installer` fetches the locked Debian snapshot Release/signature and installer checksums, verifies Debian archive signatures and the entire digest chain, then atomically promotes the six required amd64 text/graphical installer files into the ignored cache. Existing mismatched components fail rather than being silently replaced. Temporary verification/download files are removed after success or failure. This is an input preparation operation, never disk-write authority.
